- The centrepiece worked example turned out richer than planned: subgrouping the identical 100 values by production order (naive, mixing two mould cavities in every subgroup) versus by cavity (rational) doesn't just change R̄ — the rational grouping's primary 3-sigma rule only catches 3 of 20 points, but the supplementary run rules (WE4 "8 in a row on one side," WE2, WE3) unambiguously catch the full pattern, which is a genuine, better argument for teaching multiple rules than anything invented for the purpose. Checked this by pulling the actual `chart.rules_x` object from `results/m05-subgroup-rational.json` rather than assuming the shift would show as "every point in the second half beyond the limits" (it does not: the limits are still centred on the *grand* mean of both cavities, which sits between the two, and the primary rule only fires on the few points from either cavity that swing far enough past it by chance) — worth remembering for any future module that invents a similar shift-detection example: don't narrate the expected mechanism without checking the actual per-point rule output.
- No new harness kind: rational subgrouping reuses `capability` (`chart: "xbar_r"`) on the same 100 (or 40, for the exercise) values with two different subgroup-index columns; rounding loss reuses `descriptive` on the same values rounded two ways. - **A real error caught and fixed before committing:** the descriptive-statistics calculator on the rounding-loss example was first preloaded with a hand-typed array (mean 6.5001, s 0.00436) that did not match the registered `m05-rounding-coarse` dataset (mean 6.4998, s 0.00763) — a transcription slip when constructing the calculator's JSON by hand instead of extracting it from the CSV. Caught by comparing the calculator's live output against the page's own stated numbers during the browser check, not by any automated script (`sanity.py` cannot see inside a `<script class="calc-data">` JSON blob, only `data-ex` spans). Fixed, and separately re-verified programmatically that the two control-chart calculators' embedded arrays and the two hand-built HTML data tables (Table 1, Table 2 — 100 values each) exactly match their source CSVs, since those were also transcribed by hand from a script's printed output rather than generated by a template. **Lesson for future modules:** any raw data embedded in a calculator's `calc-data` JSON or in an HTML table needs to be extracted programmatically (e.g. `json.dumps` straight from the CSV) and, ideally, diffed against the CSV after pasting into the page, not eyeballed — `sanity.py`'s traceability check only covers `data-ex` spans and does not, and cannot, validate a calculator's preloaded dataset or a plain data table against the source CSV.
